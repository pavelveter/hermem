# ADR-035: Entity and Task ID Generation Strategy

## Status

Accepted (2026-08-22 — pulled into the v0.4.0 facade-removal release by
release-manager decision; the legacy-ID re-key/alias-table migration remains
governed by ADR-033 as a follow-up)

## Context

IDs today come from three incompatible sources:

1. **`core.NewTaskID()`** — `task-%d` from a **process-local atomic
   counter** starting at 0. Every process (server, each CLI invocation,
   each MCP stdio session) mints the same sequence. `task-1` from the
   CLI collides with `task-1` from the server. Callers span 5 packages
   (`server/task`, `cli/task`, `mcp/tools`, `compression`).
2. **LLM-chosen entity IDs** — `ExtractedEntity.ID` is generated by the
   extraction model (prompt-instructed), so ID stability/collision
   behavior depends on model whims.
3. **Client-chosen IDs** — the Python plugin already changed its scheme
   once (`mem-<8hex>` → `mem-<16hex>`), leaving a documented permanent
   dedup split: "pre-v0.5.0 rows will NOT dedup-merge with new writes"
   (`plugins/memory/hermem/plugin.yaml`).

IDs are also used as **primary keys, edge endpoints, vector-index keys,
and idempotency references** — they are the federation fabric of the
whole system.

## Why the current design breaks

1. **Active collision bug.** Two writers (a long-running server + any
   CLI command, or two MCP agent processes — the normal deployment!)
   mint identical task IDs. `INSERT OR REPLACE` semantics then silently
   overwrite one task with another. This is already live, it just needs
   two processes to matter.
2. **No global uniqueness = no federation.** Cross-deployment features
   (sync, import/export merge, shared team memory) require IDs that are
   unique without coordination.
3. **No time-order.** Random/counter IDs can't be sorted by creation;
   keyset pagination and incremental sync need time-ordered IDs.
4. **Content-addressing is done ad-hoc by clients.** Each SDK/plugin
   invents its own hash format (the `mem-` incident), so dedup never
   works across clients — the exact opposite of a memory system's goal.
5. **LLM-minted IDs are unaccountable.** The model decides identity;
   re-extraction of the same text may or may not produce the same ID.

## Decision

1. **Server-minted, time-ordered unique IDs:** UUIDv7 (or ULID) for
   every server-generated ID (tasks, episodes, jobs, edges where
   applicable). Generated in ONE place — the domain service — never in
   transport shells (`server/task` currently fills IDs; that moves down).
2. **Deterministic entity identity (content-addressed):**
   `entity_id = "ent-" + base32(sha256(normalize(content) | category | tenant | model_ns))[:26]`.
   - `normalize` = the existing Unicode/whitespace normalization
     (`core/normalize.go`) made canonical and versioned.
   - Same content + same scope ⇒ same ID ⇒ dedup is an insert-or-ignore,
     not a similarity search. Vector-similarity dedup remains as a
     *merge suggestion* layer, not identity.
   - The scheme is documented and implemented in all SDKs so
     client-side pre-dedup matches server-side identity.
3. **LLM never mints IDs.** Extraction returns content/relations only;
   the pipeline assigns IDs. (Relation targets resolve by content hash
   or explicit reference.)
4. **ID format registry:** one validated grammar
   (`<type>-<26–32 base32 chars>`), a `hermem id inspect` debugging
   command, and a migration (ADR-033 data-migration) that re-keys
   legacy counter tasks to UUIDv7 with an alias table for old
   references.

## Alternatives considered

1. **UUIDv4 everywhere.** Simple and unique, but not time-ordered —
   hurts index locality and pagination. Rejected in favor of v7.
2. **Keep client-minted IDs, document uniqueness duty.** Rejected:
   already failed once (`mem-` split); clients can't be trusted to
   coordinate.
3. **Snowflake-style (node ID + counter).** Requires node-ID allocation
   — coordination we don't have across 5000 deployments. Rejected.
4. **Similarity-based identity (embedding hash).** Rejected: embeddings
   change with model versions; identity must not depend on the model.

## Tradeoffs

- **Re-keying migration is invasive** (PK + FK + edges + vector index);
  mitigated by the alias table and chunked backfill (ADR-033).
- **Content-hash identity makes edits create new entities** — that's a
  *feature* for a versioned memory (old content keeps its ID and can be
  superseded via the evolution subsystem), but it surprises users
  expecting in-place rename; documented explicitly.
- **26-char IDs are longer** than `task-1` in logs/UX; accepted (ULIDs
  are the industry norm; CLI displays short prefixes where unambiguous).
- **Determinism couples ID to normalization version** — bumping
  normalization changes IDs, so the normalizer is version-locked and
  the version is part of the hash input.

## Consequences

- The silent-overwrite collision class is eliminated.
- Dedup becomes deterministic and cross-client consistent — the
  `mem-<8hex>` incident class cannot recur.
- Time-ordered IDs enable incremental sync, keyset pagination, and
  efficient `ORDER BY id` recency scans.
- Federation/import-merge features have a sound identity foundation.
